## Fix notes

N1. src/Dhadgar.Nodes/Auth/ForwardedClientCertificateMiddleware.cs:100-101 (and :48-52) — The accepted certificate is written to `context.Connection.ClientCertificate` and never cleared. With Kestrel TLS, `ITlsConnectionFeature` is connection-scoped, so the value outlives the request (and HTTP/2 streams share it). The Gateway pools connections to Nodes and multiplexes many agents over them. Concrete state: request 1 from the Gateway carries agent A's cert, so the connection now holds cert A. Request 2 on the same connection carries agent B's header. The rule "a certificate from the TLS handshake always wins" (line ~83) sees cert A as the connection's own certificate and keeps it, so `MtlsMiddleware` authenticates request 2 as node A. A request with no header also authenticates as A. `RegisterForDispose` also disposes the cert after response 1 while the feature still points at it (ObjectDisposedException or use of a disposed cert on request 2). The unit tests use `DefaultHttpContext`, which cannot show this. — Change: record `var accepted = false;` in `TryAcceptCertificate` (make it return bool, or return the certificate). In `InvokeAsync` call `try { await _next(context); } finally { if (accepted) { context.Connection.ClientCertificate = null; } }`. Never leave a forwarded certificate on the connection after the request ends. Capture the same "own certificate" check before assignment, so a restored null is correct. Update `InvokeAsync_TrustedIpWithValidHeader_SetsCertificateAndRemovesHeader` to read `ClientCertificate` inside `next` (it currently asserts after `InvokeAsync` returns). Keep `RegisterForDispose`. — verify: (a) unit test with a `TlsConnectionFeature` pre-set on the context's features: after `InvokeAsync` returns, `context.Connection.ClientCertificate` is null; (b) a Kestrel HTTPS (or `TestServer` with a shared feature) test that sends request 1 with cert A in the header and request 2 over the same connection with cert B in the header, and asserts request 2's `Items["NodeId"]` is B's node. Revert check: without the `finally`, (b) sees A.

N2. src/Dhadgar.Nodes/Auth/MtlsMiddleware.cs:266-278 (startup validation) and src/Dhadgar.Nodes/Auth/ForwardedClientCertificateMiddleware.cs:130-140 — `IPNetwork.TryParse` accepts `0.0.0.0/0` and `::/0`. `Mtls__ForwardedCertificate__Enabled=true` with `TrustedProxies:0=0.0.0.0/0` passes startup and makes every peer a trusted proxy, so any client that can reach Nodes and has seen an agent certificate (certificates are public, sent in the handshake) can send `X-Client-Cert` and authenticate as that node. — Change: in the validation loop, throw `InvalidOperationException` (same generic message, no value echoed) when `!IPNetwork.TryParse(proxy, out var net) || net.PrefixLength == 0`. In the middleware `ParseTrustedProxies`, skip entries with `PrefixLength == 0` as well. Add to the message "a prefix length of 0 is not allowed". — verify: startup tests for `Enabled=true` with `["0.0.0.0/0"]` and `["::/0"]` each throw `InvalidOperationException`; a unit test shows the middleware built with `0.0.0.0/0` directly (bypassing startup) does not trust `10.42.1.5`.

## Not fixed

Advisory, not blocking this packet. Each needs a decision or a later packet:

- Trust model breadth (D-S210). The header is trusted from any address in `TrustedProxies`. The README example is a pod CIDR, which includes every pod. Agent certificates are public, so any pod in that CIDR can replay a captured agent cert and become that node. Recommend a `/32` (or the Gateway's own range only) plus a NetworkPolicy that limits Nodes ingress to the Gateway. Consider a Gateway-signed or shared-secret second header in a later packet.
- P06 must (a) strip any client-supplied `X-Client-Cert` before setting it, and (b) set it only from a certificate that completed the TLS client-auth handshake (proof of possession), never from a request header or body.
- `RequireClientCertificate=false` (allowed in production) lets `/hubs/agent` pass `MtlsMiddleware` with no principal. P04 must put `[Authorize(Policy = "AgentPolicy")]` on the hub and derive `NodeIdClaim` only from the validated `node_id` claim. `Mtls:Enabled=false` (Development only, enforced at startup) does the same.
- `AddAuthentication(AgentMtls)` sets `DefaultScheme` for the whole service. If a later packet adds another `AddAuthentication(...)` (JWT, admin API key), the last call wins. Register a scheme explicitly in policies, or order the calls deliberately.
- Pre-existing (not in this diff): `CertificateAuthorityService.ValidateCertificateAsync` accepts a CA-signed certificate that has no `AgentCertificates` row (it only rejects rows marked revoked), and `CertificateValidationService` does not bind the thumbprint to the node record or check node status. P04 should look the node up and reject decommissioned nodes before accepting a hub connection.
- A certificate from the Gateway-to-Nodes TLS handshake (for example Gateway's own service certificate) would win over the forwarded certificate by design and then fail SPIFFE validation. Functional, not a security problem, but D-S210 should say that Nodes' Gateway-facing listener must not request client certificates.
- Checked and fine: header removed in every case before `next`; header ignored when `Enabled=false`; IPv4-mapped normalisation; `/hubs/agentx` not protected, `/hubs/agent/negotiate` protected via `StartsWithSegments`; no cert value logged; only `FormatException`/`CryptographicException` caught; problem+json shapes; `Enabled=true` with empty or unparsable list fails startup; revocation is checked in `ValidateCertificateAsync` so the README claim holds.
